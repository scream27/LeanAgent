변경된 실행 정책: Lean 검증 시간제한 없음

앞으로 Lean 검증의 wall-clock 제한은 두지 않는다. 설정은 lean.timeout_seconds: null이다. 완료될 때까지 기다리고, heartbeat는 기존처럼 측정해 후보 점수에 반영한다. 별도의 실행 시간 감점을 추가하지 않는다.

아래 180초는 대회 규정이 아니라 당시 실험에서 운영상 설정한 제한이다. 사용자 요청에 따라 제거했다. 기존 timeout 사례·재시도 점수는 이 과거 설정 아래의 기록으로 보존하며, 무제한 실행에서 retry 정책이 더 낫다는 근거로 일반화하지 않는다. 무제한 설정으로 29문제를 다시 실행한 결과는 아직 없다.

사용자가 중단한 실행이나 외부 프로세스 종료는 증명 오류와 구분한다. 기존 모델 통신 대기 설정과 프로젝트 자체의 Lean 설정은 별개이며, 이번 변경은 하네스가 Lean 프로세스를 시간으로 강제 종료하던 제한을 제거한다.

실제로 어디까지 돌렸나?

실제 데이터로 하네스 → Lean 검증 → LLM 피드백 수정은 실행했다.
그러나 기존에 설계한 자동 로컬 수리 에이전트를 전체 문제에 연결한 실험은 아니다. LLM 없는 회복은 별도 스크립트로 수행한 동일 코드 재시도·재선택이다.

따라서 ‘수리 성공률’ 하나로 합치면 안 된다. 증명 수정 성공, 검증 재시도 회복, 실행기 보정, 최종 점수 개선은 각각 별도 결과다.

Timeout은 정확히 무엇인가?

이번 로그의 kind: timeout은 Lean을 실행한 명령 하나가 벽시계 시간 180초 안에 종료되지 않아 하네스가 프로세스 그룹을 종료했다는 뜻이다. 종료 처리 때문에 기록은 180.1초처럼 조금 길 수 있다. 모델 응답 대기 timeout이나 Lean 내부 heartbeat 한도 초과를 뜻하지 않는다.

후보 하나의 주 버전 검증은 check → measure-1 → measure-2 → measure-3 순서다. 각 명령에 180초가 따로 적용된다. 첫 단계는 계측 옵션을 넣지 않은 일반 컴파일, 뒤 세 단계는 새 프로세스의 heartbeat·공리 계측이다. 하나라도 실패하면 그 후보는 해당 실행에서 유효 처리되지 않는다.

여기서는 파일 전체를 컴파일하므로 timeout에는 import 로딩과 주변 선언 처리도 포함된다. 반면 점수의 heartbeat는 대상 선언을 감싼 계측 구간의 값이다. 따라서 ‘180초 초과’와 ‘대상 증명이 논리적으로 틀림’ 또는 ‘대상 heartbeat가 큼’은 같은 판정이 아니다.

원인을 확정한 것은 아니다. 동일 코드·동일 제한 재시도의 성공은 관측했다. 자원 경합, 캐시 상태, 파일 전체 처리 비용 중 무엇이 어느 정도 원인이었는지를 분리한 실험은 하지 않았다. P18 원본은 timeout 뒤 재시도에서 sorryAx가 확인됐으므로, 재시도가 항상 유효한 증명을 회수하는 것도 아니다.
