1. 무엇을 연결했나

공용 하네스의 입력·선택·기록 로직은 그대로 사용했다. run(evaluator=...)에 Strata 준비 환경 어댑터를 연결하고, 최초 후보 평가 뒤 제한된 자동 수리·정리를 적용했다.

JSON 후보 → 전체 Lean 검증 → 남은 목표 수리 / 한 줄 정리 → 전체 재검증·3회 계측 → 최선 보존 → 최종 재검증

모델 응답은 proof 본문 하나이다. 명제·imports·주변 원문은 고정했다. 이전에 본 문제이며 역사적 증명에서 얻은 전략을 포함한다. 독립 모델 성능평가는 아니다.

2. 실제 점수

문제토큰: 원본 → 후보 선택 → 로컬 후HB / 1000: 같은 순서선택 점수: 전 → 후최종 재검증 점수
P1313 → 46 → 465173.270 → 4659.128 → 4659.12865.081 → 65.08165.081
P2222 → 43 → 432694.959 → 2496.446 → 2496.44662.666 → 62.66662.666

선택 점수는 탐색 중 측정한 값, 최종 재검증 점수는 선택 뒤 새 프로세스에서 다시 측정한 값이다. 작은 HB 차이를 별도의 개선으로 주장하지 않는다.

공용 cost = ½ × (토큰 비율 + HB 비율), 작을수록 좋음. 두 문제의 robustness가 1이므로 로컬 final score = 100 − ⅔ × 100 × cost. 공식 서버 점수는 아니다.

3. 후보와 원문 오류를 직접 보기

      intros x Hin
      simp_all

4. 로컬 처리 결과

실패 후보에는 남은 목표에 assumption/rfl/exact?/simp? 및 고정된 subset 조합을 시도했다. P1에서는 quant/app/ite/eq 같은 분기에 목표가 남았고, P2에서도 같은 종류의 목록 포함 추론이 남았다. 유효 후보에는 지원되는 독립 한 줄의 삭제·simp 명시화를 시도했다. query 실행 자체는 최종 후보에서 제외하고, 한 줄 제안을 추출했을 때만 다시 전체 검증했다.

선택 효과와 로컬 성공은 다르다. 보수적인 긴 증명에서 한 줄을 줄여 검증에 성공해도 이미 더 좋은 후보가 있으면 최종 선택은 바뀌지 않는다. 따라서 valid 시도 수와 최종 점수 증가를 별도로 기록했다.

첫 번째 짧은 후보들은 귀납 뒤 넓은 단순화만으로 목표를 닫지 못했다. 뒤에 solver를 붙이는 방식은 앞선 구조적 선택을 복구하는 데 한계가 있다. 상세 원문 진단은 위에서 확인할 수 있다.

diagnostics.py는 첫 오류·위치·goal 텍스트를 보존하는 결정적 피드백을 만든다. 이것은 실제 tactic-state 인증과 다르며, 기존 공용 루프의 피드백을 이번 실험 중 교체하지는 않았다.

남은 목표를 사람 말로 풀면

P2의 quant 분기에 남은 목표는 아래와 같은 구조다. 실제 진단의 긴 타입·변수 이름만 줄여 썼다.

가설 1: x가 A에 있으면 x는 A′에도 있다.
가설 2: x가 B에 있으면 x는 B′에도 있다.
목표: x가 A 또는 B에 있으면, x는 A′ 또는 B′에 있다.

사람은 “A인 경우 / B인 경우”를 나눠 해당 가설을 적용한다. 하지만 넓은 simp만으로 이 추론이 끝나지는 않았다. subset을 너무 일찍 펼치면 기존 subset 결합 연산도 바로 적용하기 어렵다. 연산을 더 많이 반복하는 것보다 현재 목표 형태에 맞게 선택하는 것이 다음 실험 과제다.

후속 실험: JSON 진단으로 제안 복구

일반 텍스트에는 위치가 없었던 제안 2건을 Lean의 JSON 진단으로 다시 받았다. 2/2 명시적 증명이 전체 검증에 통과했다. solver가 새로 해결한 문제가 아니라, 이미 나온 제안을 안전하게 회수한 것이다.

simp? at m    → simp only at m
simp? at name → simp only at name

두 후보 모두 기존 최선보다 점수가 낮아 최종 선택은 유지했다. 고정된 18회 로컬 처리와 구분한 탐색적 후속 실험이다.

5. 다음에 바꿀 부분

  1. 오류 앞부분과 goal을 보존: 공용 평가기는 긴 로그의 마지막 4,000자만 오류에 담는다. 실제 P1의 6,186자 로그에서 최초 quant 분기가 공용 피드백에서 사라졌다. 추가한 diagnostics.py는 그 첫 목표를 보존한다. P2에서는 같은 누락이 관측되지 않았다.
  2. 명세·정의 문맥 연결: 모델 요청에는 문제와 이전 피드백은 있지만 전체 template·import된 정의 본문이 자동으로 들어가지 않는다. 로컬 검색 결과를 명시적으로 공급해야 한다.
  3. 진단에 맞는 수리 선택: 이미 실패한 tactic 뒤에 solver를 붙이는 방법은 구조적인 잘못을 복구하지 못할 수 있다. 블록 재작성과 분기·귀납 선택은 별도 문제다.
  4. 제안 위치와 다중 goal 구분: 한 줄 query 제안을 보수적으로 추출한다. 여러 goal의 제안들을 하나의 script라고 합쳐 제출하지 않는다.
  5. 프로토콜 어댑터: 기존 escalation은 status/proof_body를 반환하도록 요청하지만 공용 하네스는 proof 하나만 받는다. candidate만 변환하고 need_context/no_candidate는 별도 제어 신호로 처리해야 한다.
  6. 최종 실패 fallback: 공용 코드가 마지막 검증 실패를 표시하기는 하지만 자동으로 차선 후보를 다시 검증해 반환하지는 않는다. 이번에 관측된 실패가 아닌 코드상 개선 지점이다.
