# Lean Refactor Arena 에이전트 아키텍처

> 논의 초안 · 2026-10-21
>
> 에이전트가 볼 수 있는 정보와 실행할 수 있는 동작의 경계를 먼저 정의합니다.
> Docker 사용 여부와 세부 인터페이스는 파일럿 검증 후 결정합니다. 아래 내용은 구현 완료를 뜻하지 않습니다.

## 1. 목적과 설계 원칙

이 저장소는 Lean Refactor Arena에 참가할 에이전트와 전체 실행 코드를 개발합니다.
최종 증명과 함께 코드를 제출하며, 고정된 입력·환경·예산에서 실행을 재현할 수 있도록 구성합니다.

먼저 다음 세 가지를 구분합니다.

| 구분 | 해결할 문제 | 적용할 위치 |
| --- | --- | --- |
| 정보 접근 | 기존 개선 풀이와 다른 실행의 기록이 현재 실험에 들어오지 않도록 제한 | 입력 준비, 문맥 구성, 도구, 파일·네트워크 접근 정책 |
| 실행 상태 | 문제별 메모리와 비용을 분리하고 중단 후에도 일관되게 복원 | 하네스의 상태·기록·비용 관리 |
| 실행 환경 | 동일한 Lean 버전·의존성·옵션으로 검증 | 환경 명세와 Lean 실행기 |

Docker나 VM을 사용해도 전달한 프롬프트에 기존 풀이가 포함되거나 비용 기록이 누락되면
실험 조건은 유지되지 않습니다. 각 경계를 코드와 실행 환경에서 별도로 적용합니다.

## 2. 개발과 대회 실행의 경계

| 구분 | 실행 주체 | 접근과 결과의 범위 |
| --- | --- | --- |
| 저장소 개발 | 팀원 개인 계정의 코딩 에이전트 CLI | 코드·문서·개발 자료를 이용해 구현과 오류 분석 수행 |
| 독립 풀이 탐색 | 격리된 환경에서 실행하는 개인 CLI | 허용된 문제·소스만 제공하고 새 대화와 작업 공간 사용. 개발·탐색 결과로 기록 |
| 비교 평가·제출용 실행 | OpenRouter 기반 API 에이전트와 공통 하네스 | 고정 입력·도구·환경·예산으로 실행하고 비용과 검증 결과 기록 |

저장소를 개발하는 CLI의 대화와 프로젝트 메모리는 제출용 실행의 입력이 아닙니다.
독립적인 풀이 능력을 비교하려는 CLI 실험에서는 CLI 자체와 그 파일·셸 도구를 함께 격리해야 합니다.
Lean 컴파일러만 격리해서는 호스트에서 실행하는 CLI의 파일 접근을 제한할 수 없습니다.

개인 구독 CLI로 얻은 풀이를 제출용 API 실행 결과로 취급하지 않습니다.
CLI를 제출용 실행기로 사용하려면 모든 내부 모델 호출의 경로·비용·재현 가능성을 별도로 검증해야 합니다.
개발 중 얻은 특정 문제의 개선 풀이가 프롬프트·예제·전략 파일에 포함되지 않도록 검토합니다.

## 3. 구성요소별 격리 경계

초기안은 단일 API 에이전트가 명시적인 도구를 호출하는 구조입니다.
모델에는 선택한 문맥과 도구 정의를 전달하고, 실제 요청의 실행 여부는 하네스가 결정합니다.

| 경계 | 허용하는 정보·동작 | 제한하는 정보·동작 | 적용 책임 |
| --- | --- | --- | --- |
| 개발 자료 → 실행 입력 | 고정된 코드·설정·일반 전략, 해당 문제와 원본 증명 | 개인 대화·기존 개선 풀이·다른 실행 결과의 자동 유입 | 입력 준비기와 입력 목록 검토 |
| 하네스 → 모델 | 현재 문제 문맥, 선택한 실행 기록, 도구 정의, 남은 예산 | 전체 저장소·전체 기록·인증정보 전달 | 문맥 구성기와 모델 연결 계층 |
| 모델 → 도구 | 해당 실행에 연결된 소스 검색·후보 저장·검증 요청 | 임의 호스트 경로·셸·환경 선택, 다른 실행 ID 지정 | 도구 요청 검증과 실행 범위 연결 |
| 도구 → Lean 실행기 | 저장된 후보와 하네스가 고정한 환경 | 모델이 지정하는 compiler·명령·의존성·실행 디렉터리 | Lean 실행기 |
| Lean 프로세스 → 호스트 | 필요한 도구·라이브러리·현재 검증 입력과 임시 공간 | 기존 풀이, 다른 실행, 인증정보, 불필요한 네트워크 접근 | OS 수준의 실행 격리 |
| 실행 → 기록 저장소 | 하네스를 통한 후보·이벤트·비용·검증 결과 저장 | 에이전트가 비용·검증 결과·최종 선택 기록을 직접 수정 | 기록 관리자와 파일 권한 |
| 문제 A → 문제 B | 실행 전에 고정한 공통 코드·일반 전략·허용 라이브러리 | 후보·작업 메모리·대화·실행 중 학습 결과 공유 | 문제별 상태 분리 |

여기서 신뢰하는 실행 주체는 검토·고정된 하네스와 실행기입니다.
모델 출력과 생성된 Lean 코드는 외부 입력으로 다룹니다.
실험 코드 자체가 임의 Python이나 셸을 실행한다면, 도구 인자 검사만으로 접근을 제한할 수 없습니다.
이 경우에는 실험 프로세스 전체에 OS 수준의 격리를 적용해야 합니다.

이 설계는 파일·도구·대화·실행 기록을 통한 풀이 유입을 통제합니다.
모델이 사전학습에서 이미 알고 있는 내용까지 제거한다는 의미는 아닙니다.

### 3.1 입력과 파일 접근

문제에서 제공하는 원본 증명과 필수 문맥은 허용 입력입니다.
팀원이 만든 개선 후보, 과거 제출 증명, 다른 실험의 로그와 메모리는 제외합니다.

`experiments/`에는 실험 정의를 보관하고, 실제 작업 공간은 저장소 밖에 실행별로 생성합니다.
전체 저장소를 복사한 뒤 일부를 삭제하기보다 허용 목록의 파일만 전달합니다.
실행 입력 목록에는 파일 출처·해시와 코드·설정·환경 버전을 기록합니다.

```text
에이전트에 제공할 논리적 작업 공간
├── problem/       # 해당 문제·원본 증명·필수 문맥 — 읽기 전용
├── sources/       # 허용 라이브러리 소스 — 읽기 전용
└── workspace/     # 현재 실행의 후보·메모·임시 파일
```

이 트리는 접근 범위를 설명하며, 폴더 생성만으로 격리가 구현되지는 않습니다.
읽기 전용도 파일 내용을 숨기지는 않으므로 비공개 자료에는 읽기 접근 자체를 차단합니다.
저장소 전체, `.git`, 개인 홈, 전체 `runs/`와 `submissions/`는 제공하지 않습니다.

소스 읽기는 허용된 소스 ID와 상대 경로를 기준으로 처리합니다.
상위 경로 이동·절대 경로·심볼릭 링크를 통한 범위 이탈을 검사하고,
파일 권한이나 격리된 파일시스템으로 접근 범위를 뒷받침합니다.
검색 인덱스와 공유 캐시에도 같은 입력 정책을 적용합니다.
고정된 의존성 캐시는 읽기 전용으로 재사용할 수 있지만, 후보와 실행 중 생성한 캐시는 실행별로 분리합니다.

현재 데이터 준비 도구는 `scripts/corpus.py`입니다. 출처·revision별 압축 코퍼스에서 선택한
문제의 원본 파일과 해당 소스 파일 전체를 꺼내고, `selection.json`에 입력 해시를 기록합니다.
원본 소스 파일에 포함된 다른 선언의 노출 범위는 실행 정책에서 검토합니다.
이 도구는 OS 격리나 Lean 의존성 설치를 수행하지 않습니다.

`data/raw/`와 `runs/`에는 과거 검증·개선 후보가 있으므로 실행 입력에서 제외합니다.
기존 분석용 legacy 복원 공간 역시 전체 코퍼스와 과거 결과를 포함하므로 에이전트 입력이 아닙니다.

### 3.2 도구와 Lean 실행

초기 도구는 소스 읽기, 관련 정리 검색, 후보 저장, 검증·평가 요청으로 제한하는 안을 제안합니다.
임의 셸은 초기 API 에이전트에 제공하지 않습니다. 도구 이름과 인자 형식은 미정입니다.

도구는 현재 실행과 문제에 미리 연결됩니다. 모델이 보낸 실행 ID나 환경 ID만으로 접근을 허용하지 않습니다.
후보는 저장 시 해시로 식별하고, 검증 결과도 같은 후보 해시에 연결합니다.
도구 반환값에는 필요한 오류·측정값과 현재 실행의 자료만 포함합니다.

Lean은 생성된 코드를 처리하는 별도 프로세스로 실행합니다.
허용 파일·쓰기 공간·네트워크·CPU·메모리·시간 제한을 적용하는 실행 방식을 파일럿에서 검증합니다.
금지 구문 검사나 도구의 경로 검사는 OS 수준의 실행 격리를 대체하지 않습니다.
환경 준비 실패와 증명 실패는 구분해 기록합니다.

### 3.3 인증과 네트워크

제출용 API 인증은 모델 연결 계층이 관리하고, 프롬프트·후보·Lean 프로세스에 전달하지 않습니다.
제출용 모델 호출은 OpenRouter로 모으고, 도구나 서브에이전트가 별도 경로로 호출하지 않도록 구성합니다.
Lean 의존성은 준비 단계에서 확보하고, 검증 프로세스는 외부 네트워크 없이 실행하는 안을 제안합니다.

CLI 실험은 CLI별 로그인 방식을 확인해야 합니다. 개인 설정 디렉터리 전체를 공유하는 대신
필요한 인증만 별도로 구성하고 대화·메모리는 새로 시작합니다.
호스트 파일 도구, MCP, SSH 연결, Git 인증 등 격리 밖에 접근할 수 있는 경로를 함께 점검합니다.
모델·인증 통신을 허용하면서 외부 풀이 검색을 제한하는 네트워크 정책은 별도 검증 대상입니다.

## 4. 메모리와 기록의 경계

| 종류 | 초기 정책 |
| --- | --- |
| 공통 지식·전략 | 실행 전 버전 고정. 일반 전략과 도구 사용법을 코드와 함께 보존 |
| 문제별 작업 메모리 | 현재 계획·실패한 접근·관련 정리. 해당 실행 안에서만 사용 |
| 후보·검증 기록 | 원본 파일과 검증 근거 보존. 모델에는 필요한 부분만 전달 |
| 문제 간 학습 메모리 | 초기 버전에서 사용하지 않음 |
| 개인 CLI 메모리 | 비교 평가·제출용 실행에 가져오지 않음 |

초기에는 모델 요약 없이 문제·원본 증명, 현재 최선 후보·검증 지표,
최근 시도·오류, 실패한 접근의 간단한 기록, 남은 예산을 선택해 문맥을 구성합니다.
전체 로그는 보존하되 모델 입력에서 오래된 내용을 제외할 수 있습니다.

에이전트는 작업 메모를 작성할 수 있지만, 검증 결과와 비용 장부를 직접 수정할 수 없습니다.
요약 메모가 원본 후보나 실제 검증 결과를 대체하지 않도록 합니다.
모델 기반 요약을 도입하면 그 비용도 해당 문제에 합산합니다.
메모리 없음·실패 기록 유지·모델 요약 사용은 동일 예산에서 비교할 실험 항목입니다.

새 실행은 초기 입력에서 시작합니다. 같은 실행의 재개는 기존 메모리·후보·로그·비용을 함께 복원합니다.
문제 간 메모리의 허용 범위, 실행 순서와 생성 비용 배분은 공식 기준을 확인한 후 논의합니다.
독립 실행은 초기 설계 선택이며, 공식 규칙에 메모리 공유 금지가 명시됐다는 뜻은 아닙니다.

## 5. 비용과 재현성의 경계

2026-10-21에 확인한 Track 1 안내 기준이며, 제출 전 최신 규칙을 다시 확인합니다.

| 항목 | 확인한 조건 |
| --- | --- |
| 모델 호출 | 모든 모델 호출은 OpenRouter 경유. 직접 provider API는 허용하지 않음 |
| 비용 | 공개 정가 기준 문제당 최대 US$3 |
| 집계 | 재시도와 폐기한 후보를 포함한 모든 호출 |
| 공개·제출 | 사용 모델 공개, 증명 JSONL·전체 하네스 코드·기술 보고서 제출 |
| 재현 | 고정 Lean 버전·의존성과 정확한 실행 절차 제공 |

근거: [공식 Arena 규칙 소스](https://huggingface.co/spaces/delta-lab-ai/lean-refactor-arena/blob/main/app.py).

계획·후보 생성·수리·요약·서브에이전트·모델 기반 평가를 모두 하나의 문제별 비용 장부에 기록합니다.
embedding·reranker·judge를 사용하면 모델 공개와 호출 집계 대상에 포함합니다.
호출 ID, 문제·실행 ID, 모델·provider, 사용량, 가격 근거, 비용과 응답 상태를 보존합니다.
미확정 요청은 비용 0으로 처리하지 않습니다.

새 호출 전에 남은 예산과 최대 출력 제한을 확인합니다.
병렬 호출은 공유 예산을 예약한 뒤 실제 비용으로 정산하는 방식이 필요합니다.
예산을 초과하지 않는 호출 허용 기준과 미확정 비용 처리 방식은 구현 전에 확정합니다.

중단 후에는 진행 중이던 요청과 검증 작업의 상태를 확인하고 누적 비용을 유지한 채 재개합니다.
새 실행 ID로 이전 후보 생성 비용을 숨기거나 기존 풀이의 출처를 없애지 않습니다.
개발 단계의 문제별 탐색과 여러 실행 중 후보 선택에 대한 비용 처리 기준은 추가 확인 사항입니다.

최종 선택은 검증된 후보와 고정된 정책으로 결정합니다.
제출 파일의 증명이 재검증한 후보와 동일한지 확인하고 코드·입력·환경·설정·호출 기록을 연결합니다.
모델 응답의 변동성을 고려해 재실행 절차와 실제 실행 근거를 보존합니다.

## 6. 실행 흐름과 구현 위치

```text
실험 정의 → 허용 입력 목록·환경·예산 고정 → 독립 실행 상태 생성
  → 원본 검증·기준값 측정
  → 문맥 구성 → API 에이전트의 행동 선택
  → 도구 요청 검사 → 제한된 소스 접근 또는 격리된 Lean 실행
  → 후보·관측·비용 기록 → 문맥 갱신 ↺
  → 종료 → 최종 재검증·선택 → 결과 수집·제출 산출물 생성
```

| 위치 | 책임 |
| --- | --- |
| `src/lean_agent/agents/` | 다음 행동 결정, 탐색·수리 전략 |
| `src/lean_agent/harness/` | 입력·실행 연결, 상태·예산·기록·재개와 도구 실행 제어 |
| `src/lean_agent/models/` | OpenRouter 연결, 인증과 호출 사용량 수집 |
| `src/lean_agent/tools/` | 에이전트용 도구와 인자·접근 범위 검사 |
| `src/lean_agent/context/` | 허용된 문맥 선택과 메모리 관리 |
| `src/lean_agent/lean/` | 고정 환경과 Lean 프로세스 실행·격리 |
| `src/lean_agent/evaluation/` | 실제 검증 결과 판정, 측정값과 후보 선택 |
| `data/corpora/` | 출처·revision별 원본 레코드와 문맥, 환경·무결성 명세 |
| `benchmarks/arena/` | 공식 문제·평가 코드의 수집 스냅샷 |
| `scripts/corpus.py` | 선택한 원본 입력 추출과 저장 무결성 확인 |
| `experiments/<실험명>/` | 목적·방법·실행법·결론, 실험 코드·설정 |
| `runs/` | 실행기가 수집한 결과. 에이전트에 전체 경로를 노출하지 않음 |
| `submissions/` | 최종 증명·선택 근거·재현 설정 |

패키지명과 세부 배치는 가안입니다. 전체 폴더 구조는 README의 초안을 따릅니다.
`AGENTS.md`는 저장소를 개발하는 코딩 에이전트의 규칙으로 작성하고,
대회 에이전트 지침은 `src/lean_agent/prompts/`에서 별도로 관리합니다.

## 7. 격리 방식 선택과 파일럿

Docker는 필수 조건으로 두지 않습니다. 위 경계를 충족하는지 검증한 후 실행 방식을 선택합니다.

| 선택지 | 활용 조건과 검토 사항 |
| --- | --- |
| 로컬 하네스 + 제한된 API 도구 | 임의 셸 없이 입력·도구를 통제하는 초기 개발. Lean 프로세스 격리는 별도로 필요 |
| Linux Bubblewrap | 허용 파일과 프로세스 범위를 제한하는 정책을 구성할 수 있는 Linux 환경 |
| Docker | 고정 환경 배포와 실행별 파일·프로세스 격리를 함께 운영할 경우 |
| 가상머신 | 개인 CLI와 도구를 포함한 OS 환경을 분리할 경우 |
| 별도 OS 계정 | 파일 권한·공유 경로·관리자 권한을 통제할 수 있을 때 검토. 계정 생성만으로 충분하지 않음 |

하네스의 전략·메모리·비용 관리가 특정 격리 도구에 종속되지 않도록 실행기와 분리합니다.
초기부터 모든 실행 방식을 구현하지 않고, 한 문제로 필요한 경계를 검증합니다.

| 파일럿 검증 | 기대 결과 |
| --- | --- |
| 호스트·다른 실행에 둔 테스트 파일 읽기 | 접근 실패, 내용이 도구·Lean 출력에도 노출되지 않음 |
| 상위 경로·절대 경로·외부 심볼릭 링크 요청 | 허용 범위 밖 접근 거절 |
| 원본·고정 의존성·검증 기록·비용 장부 수정 시도 | 에이전트와 Lean 프로세스의 직접 수정 거절 |
| 새 실행 시작 | 이전 대화·후보·메모리 미유입 |
| 중단된 실행 재개 | 기존 상태와 비용 유지, 미확정 요청 확인 |
| 모델·검증 프로세스의 네트워크 접근 | 각 역할에 허용한 연결만 가능 |
| 환경·후보 연결 확인 | 지정 환경에서 저장된 동일 후보를 검증 |

격리가 없는 로컬 기능 테스트를 격리 검증 완료로 기록하지 않습니다.
파일럿 결과를 바탕으로 지원 OS·CLI, 인증 방식, 네트워크 정책, 도구 인터페이스와
비용 처리 기준을 확정합니다. 아직 실행 환경 설치나 격리 검증은 수행하지 않았습니다.
